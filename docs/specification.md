## 3. ゲーム概要

ブラウザで遊ぶ、和風の3D漢字バトルゲーム。

ガチャで引いた漢字を採用または破棄し、採用順に4文字を作る。実在の四字熟語である必要はなく、自由な造語でよい。4文字そのものを立体化し、一体のモデルとして戦わせる。文字から生き物を生成する仕様ではない。

勝敗はポイントの合計で決まる。3Dはポイント加算と勝敗を表現するための演出であり、アクション操作や物理衝突による勝敗判定は不要。

## 4. 画面遷移

```text
ホーム → ガチャ → 試合 → リザルト
   ↕                        ├→ もう一度書く → ガチャ
 漢字一覧                   └→ ホーム
```

### ホーム

- ゲーム開始用ボタン。文言は未確定。
- ［漢字一覧］ボタン。

### 漢字一覧

- ガチャに出る全250字を、7グループ別に閲覧できる。
- 未取得の漢字も最初から表示する方針。
- ［ホーム］で戻る。
- 補填専用の数字「1」はガチャ対象ではなく、この250字に含めない。

### ガチャ

1. ［引く］を押す。
2. ガチャのアニメーションが流れる。
3. 抽選された漢字と［書く］［消す］を表示する。
4. ［書く］なら取得、［消す］なら破棄。
5. 続行条件を満たしていれば次の［引く］へ進む。

- 抽選は最大10回。書く・消すのどちらでも1回分の抽選を消費する。
- 4文字を取得した時点で即終了。残りの抽選は行わない。
- 取得した順に左から並ぶ。風→林→火→山なら「風林火山」。並べ替え機能は要求されていない。
- 同じ漢字が複数回出てもよく、重複取得も可能。
- 残り抽選回数と取得済みの文字を表示する方針。
- 10回目の漢字の採否を決めた後、4文字に届かなければ不足分を数字「1」で右側に補填する。

### 数字「1」の最優先ルール

- 補填されるのは漢数字の「一」ではなく、数字の「1」。
- 「1」が1つでも含まれれば、その4文字全体の最終合計点は必ず1点。
- 他の漢字、組み合わせ、レアリティの点数がどれだけ高くても、このルールを優先する。
- 「風林火1」「風111」「1111」はすべて全体で1点。
- 通常の漢数字「一」はガチャ対象の漢字であり、この特例を適用しない。
- 実装では補填文字と通常漢字を型または明確な識別子で区別する。

### 試合

- 敵は収録漢字からランダムに4文字を選ぶ。重複あり。ガチャの採否選択や補填はしない。
- 敵にもプレイヤーと同じ通常の得点計算を適用する。
- 配置：敵の4文字とポイントを左上、自分の4文字とポイントを右下。
- 4文字は一体となって浮遊する3Dモデル。
- 以下の順番で表示と加点を行う。
  1. 左から各漢字の文字ポイント。「風のポイント ＋○点」のように表示。
  2. 組み合わせポイント。
  3. レアリティポイント。
- 合計表示が加点ごとに増え、モデルが揺れるなどの演出を行う。
- 合計点が高い側が勝ち。同点は引き分け。
- 決着時、勝者が相手を吹き飛ばす演出。演出終了後にリザルトへ自動遷移。
- 引き分けの具体的な演出は未確定。
- 数字「1」を含む場合の途中表示方法は未確定。最終合計が必ず1点になること、例外を画面上で理解できることを守る。

### リザルト

- 四字熟語と点数を表示する。
- ［もう一度書く］でガチャからやり直す。
- ［ホーム］でホームへ戻る。
- 最後にコメントを表示する。通常コメントは複数用意する。文面は開発側で初期案を用意できる。

## 5. 得点とデータ管理

通常の合計点は次の3要素の合計。

1. 4文字それぞれの文字ポイント
2. 文字の組み合わせによる熟語ポイント（組み合わせポイント）
3. 4文字それぞれのレアリティポイント

### 確定している制約

- バトルごとに抽選し直す。
- レアリティ自体もバトルごとにランダム。文字に固定しない。
- 乱数やベクトルを数百文字分個別設定すると調整が難しいため、グループ単位で管理する。
- 漢字の分類は必ず7グループ。8グループ以上には増やさない。
- 各漢字は1つのグループに所属する。
- 漢字個別の基本データは文字と所属グループ。文字ポイントの乱数範囲と属性ベクトルは所属グループから取得する。
- 同じグループの文字でも、文字ポイントは1文字ずつ独立して抽選する方針。
- レアリティの抽選表は共通設定で管理する方針。

### 組み合わせポイント：提案段階の設計

ユーザーはベクトルの内積の使用を提案している。会話では以下の方式を提案したが、詳細な式・数値はまだ確定していない。

- 各グループに固定の属性ベクトルを持たせる。
- 4文字の全6ペアで内積を計算し、合計を相性値とする。
- 相性値にバトルごとの乱数倍率を掛けて組み合わせポイントにする。
- 同じグループだけで常に最善になるか、グループ間の関係も選択肢になるかを確認して初期設定する。

ベクトルの次元、正規化、丸め、倍率、上限、重複ペアの扱いは初期実装で明文化する。グループが7つであることと、ベクトルが7次元であることは別であり、次元数は未確定。

## 13. ルール実装と仮の初期設定（区切り3）

以下の点数・確率・相性方式の詳細は開発側が用意した初期設定であり、ユーザーが確定した数値ではない。

- ガチャと敵は250字から均等抽選し、復元抽選（同じ字の再登場・重複取得あり）とする。
- 全7グループの文字点は10〜100の整数、両端を含む。4文字それぞれ独立抽選する。
- 属性ベクトルは3次元で、計算時に長さ1に正規化する。ゼロベクトルは不可。具体値は `src/data/groups.ts` に集約。
- 組み合わせ点は4文字の位置に基づく全6ペアの正規化内積の合計 × 20 × 試合ごとの乱数倍率。倍率は0.8以上1.2未満の一様抽選。最後に四捨五入し、0〜160点へ制限する。重複した字やグループのペアも位置ごとに数える。
- この正規化内積方式では、同一グループ4字の相性値6が最大となる。混成で必ず有利になる仕組みではない。各字のランダム得点とレアリティを含む最終勝敗は別途決まる。相性設計は今後調整可能。
- レアリティは各文字独立の共通抽選。N／C／R／SR／URの重みは50／28／15／6／1（合計100）、固定加算点は0／10／30／80／200。文字には固定しない。
- 通常の加点手順は、左から文字点4件→組み合わせ点1件→左からレアリティ点4件。
- 補填文字は `kind: 'filler'`、通常漢字は `kind: 'kanji'` で区別する。補填が1つでもあれば通常得点の抽選・加算を行わず、理由を付けた合計1点の特例データを返す。通常の漢数字「一」は対象外。
- `createBattle` は敵の4字、双方の得点・手順、勝敗、結果コメントを一度に確定する。画面側は返された結果を保持し、演出時に再抽選しない。敵は補填なしで同じ通常得点関数を使用する。
- ガチャ状態は操作ごとに新しい値を返す。10回目は採否の決定後に右側へ補填し、4字取得時は直ちに終了。再戦は `createGacha` から新規作成する。
- `npm test` でデータ整合性、ガチャ境界、全15種類の補填位置パターン、得点・レアリティ境界、加点順序、勝敗・新規試合を検証する。画面・タイマー・3D演出の再戦時リセットは該当画面の実装時に確認する。
